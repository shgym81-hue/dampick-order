# 배송 묶음별 결제

## 구현된 화면

- 월·화 픽업은 해당 주 수요일 새벽, 수·목·금 픽업은 해당 주 금요일 오후로 묶습니다.
- 다음 주 상품은 다른 배송 날짜로 분리합니다. 주말·미정 날짜는 선택할 수 없습니다.
- 묶음마다 전체 선택·해제와 결제 영역으로 이동하는 버튼이 있습니다.
- 다른 묶음의 전체 선택을 누르면 이전 선택을 해제합니다. 일부 상품만 선택할 수도 있습니다.
- 결제 요약은 현재 선택한 묶음만 합산하고 배송비도 그 묶음에만 적용합니다.
- 카드결제 요청에는 선택한 신청번호·금액을 사용하며 토스 주문명에도 배송 날짜를 표시합니다.
- 요청 중에는 입력을 잠그고 중복 클릭을 차단합니다. 신청 저장은 결제 승인을 의미하지 않습니다.

## 실제 결제 전 필수 작업

1. 기존 `submit_checkout_item_request_v2`와 `confirm-toss-payment`의 운영 소스를 확보합니다. 현재 저장소에는 없으므로 승인·중복 신청 처리는 검증되지 않았습니다.
2. 테스트 Supabase에서 `database/002_scheduled_checkout.sql`을 검토·실행합니다. 이 파일은 기존 RPC를 호출하는 검증 래퍼이며 전체 백엔드 설치 파일이 아닙니다. 기존 함수가 중복·기결제 상품을 올바르게 처리하는지 확인해야 합니다.
3. 설치 성공 후 `assets/js/payment-config.js`의 `scheduledCheckoutRpc`를 `submit_scheduled_checkout_request`로 설정합니다. SQL은 기존 RPC의 직접 호출 권한을 차단하므로 화면 전환과 함께 배포해야 합니다. 설치하지 않은 상태에서는 빈 값으로 기존 기능을 유지합니다.
4. 토스에서 발급받은 테스트 클라이언트 키를 `tossClientKey`에 입력하고, 대응하는 시크릿 키는 Supabase 서버 환경변수에만 설정합니다.
5. `confirm-toss-payment`는 저장된 신청금액 검증, 토스 승인, 원자적인 상태 반영, 중복 콜백 처리를 수행해야 합니다. 기존 소스 확인 없이 새 승인 함수를 덮어쓰지 마세요.
6. 테스트 카드 승인·취소·실패 후 재시도, 동시 요청, 새로고침, 완료 상품 재선택, 관리자 반영을 확인합니다. 배송 완료 처리는 결제 확인 후에만 허용해야 합니다.

현재는 운영 DB·Edge Function 변경이나 실제 카드 승인 테스트를 수행하지 않았습니다.
래퍼를 배포하기 전의 혼합 결제 차단은 브라우저에서만 적용됩니다.
고객 인증은 기존 닉네임 방식을 유지하므로 강한 본인 인증을 제공하지 않습니다.
