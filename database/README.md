# 운영 DB 확인 목록

이 저장소만으로 현재 운영 백엔드를 완전히 복원할 수 없습니다.
아래는 프런트엔드 코드에서 확인한 의존성이며 실제 Supabase 배포 상태는 아직 확인하지 않았습니다.

## 주요 테이블

- `customers`: 고객
- `products`: 상품
- `orders`: 주문
- `order_items`: 주문별 상품
- `checkout_requests`: 결제·수령 신청
- `checkout_request_items`: 신청별 상품

## 호출 함수

| 함수 | 호출 화면 | 저장소 정의 |
|---|---|---|
| `lookup_orders_by_nickname` | 고객 주문 조회 | 구버전만 있음. 현재 화면은 상품 ID 등 최신 응답에 의존 |
| `submit_checkout_item_request_v2` | 고객 상품별 신청 | 없음 |
| `mark_card_payment_failed` | 고객 화면·결제 실패 | 없음 |
| `complete_default_pickup_item` | 결제·배송 관리 | 없음 |
| `process_checkout_request` | 결제·배송 관리 | 없음 |
| `confirm-toss-payment` (Edge Function) | 결제 성공 | 없음 |

`legacy/01_담픽_결제배송_업데이트.sql`은 주문 단위 신청을 위한 예전 코드입니다.
현재 화면은 상품 단위 신청을 사용하므로 이 SQL만 실행해서는 현재 기능이 완성되지 않습니다.
해당 SQL의 배송비 비교만 현재 화면과 동일하게 수정했습니다. 운영 DB에 반영한 것은 아닙니다.

## 다음에 확인할 항목

1. 운영 Supabase에서 최신 테이블 정의, 함수 정의, RLS 정책 및 Edge Function 소스를 확보합니다. 고객 데이터나 비밀 키는 가져오지 않습니다.
2. `submit_checkout_item_request_v2`가 상품 소유권, 중복 신청, 기결제 상품, 수량·단가·배송비를 서버에서 검증하는지 확인합니다.
3. 배송비 경계값 39,999원 / 40,000원 / 40,001원이 각각 500원 / 500원 / 0원인지 확인합니다.
4. 결제 승인 함수가 저장된 신청 금액과 결제 금액을 대조하고 중복 승인을 안전하게 처리하는지 확인합니다. 토스 시크릿 키는 서버 환경변수에만 보관합니다.
5. 관리자 권한을 별도로 검증하는지 확인합니다. 구버전 SQL의 `authenticated` 전체 허용 정책은 로그인한 모든 사용자에게 권한을 주므로, 로그인만으로 관리자임을 보장하지 않습니다.
6. 닉네임만으로 주문을 조회·신청하는 현재 방식의 공개 범위와 접근 제한을 검토합니다.

백엔드 정의를 확인하기 전에는 추측으로 대체 함수를 만들거나 구버전 SQL을 재실행하지 마세요.
